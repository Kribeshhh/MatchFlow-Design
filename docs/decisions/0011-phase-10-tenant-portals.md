# ADR 0011 — Branded public portals and verified custom domains

Accepted architecture before implementation, 2026-11-04. The user approved Cloudflare for SaaS with credentials configured later, canonical MatchFlow login/account actions, and attribution visible unless platform policy explicitly permits hiding. Stop after Phase 10.

## Authentication and tenant context

Branded portals are public browsing surfaces only. Login, player entry and organizer actions link to fixed APP_ORIGIN paths on canonical MatchFlow. Existing opaque host-only cookies and Google OIDC remain there. No cookies, tokens, cross-domain session transfer, OAuth callbacks or arbitrary return URLs are accepted on tenant hosts. This uses ordinary top-level HTTPS navigation and existing maintained OIDC rather than introducing a home-grown SSO protocol. The destination is server-built from APP_ORIGIN and validated resource IDs, never Host, Origin, query returnTo or configured navigation URLs.

Canonical `/portals/:slug` URLs serve the same public portal without a custom domain. Slug is a public locator, not authorization. Every portal query binds enabled portal → organization → PUBLIC/non-DRAFT tournament and nested resources. Existing independent reusable teams/accounts remain global resources and are not reclassified as tenant-owned; portals expose only safe approved participant summaries. Private events, share-link redemption, user APIs, developer credentials, management routes and Socket.IO are inaccessible on custom hosts even if cookies/Bearer headers are manually supplied. Existing v1 organization/event scopes remain authoritative on canonical hosts.

The server checks an exact operator-configured canonical Host allowlist before account routes. A custom host additionally needs an authenticated edge-to-origin secret, an exact active database binding, enabled portal, current DNS verification and provider hostname/certificate active status. Raw Host/X-Forwarded-Host/X-Tenant-ID do not establish authority. The edge must strip/overwrite the origin-auth header; restrict origin access and use TLS/mTLS. X-Forwarded-Host is ignored. Unknown or stale hosts fail closed before authentication or asset/SPA fallback. Custom hosts only reach the dedicated public portal API and static assets. No arbitrary-host SPA fallback.

## Branding and visibility

Organization owners/admins configure a separate Portal row, disabled by default: unique slug, title/plain-text intro, validated hex accent, approved internal navigation labels/targets, hide-attribution preference and optimistic version. MatchFlow's existing charcoal/paper visual system remains; accent contrast is validated. A platform environment policy controls whether hiding attribution is permitted. Organization logos and separate portal covers reuse private S3 and decoded/re-encoded image validation; no remote image paths, HTML, scripts or arbitrary CSS. Public portal publication is an explicit opt-in independent of the organization's public-directory profile.

## Domain lifecycle

Only the current organization owner with recent authentication can claim, verify, retry or remove a domain. Normalize IDNA hostnames, prohibit IPs, wildcards, URLs/ports, local/reserved and platform names. Use fresh random organization/claim-bound TXT challenges. Pending claims expire and can be rotated; a previous challenge/CNAME never proves a new claim. Unique active hostname claims prevent races. Require own TXT and a configured CNAME routing target before provisioning. Apex flattening requires explicit operator-configured provider apex addresses; never infer ownership from a shared IP or certificate alone.

After local proof, the Cloudflare adapter creates/looks up a custom hostname and exposes required provider ownership/certificate DNS records. Both provider hostname and ssl status must be active before routing. The adapter's API host is fixed, secrets remain server-only, response sizes/timeouts are bounded and errors are generic. Reconciliation checks DNS/provider status periodically and fails closed on loss of proof/TLS or stale checks. No provider configuration means explicit unavailability, never simulated certificates.

Removal disables routing immediately, then deletes provider configuration/certificates. Keep the hostname reserved while cleanup is uncertain. Reassignment requires confirmed cleanup, a new claim/organization-specific challenge and new provider verification. Never auto-attach a dangling DNS hostname based on CNAME alone. Domain operations use database leases/version checks around external calls, transactional state transitions and identifier-only audits; reconcile crash windows before releasing names.

Cloudflare documents separate hostname/certificate validation and both active requirements: [hostname validation](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/hostname-validation/), [API lifecycle](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/common-api-calls/), [removal](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/remove-custom-hostnames/). The integration does not certify a live deployment; zone, origin security, provider credentials, DNS/TLS and production egress/restore qualification remain operator release gates.
